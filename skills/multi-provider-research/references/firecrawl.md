# Firecrawl

Read for site inventory, bounded collection, document parsing, structured extraction, Alexandria data discovery, or requested Firecrawl work. Inspect the current callable schema: integrations can expose different subsets of Firecrawl and Alexandria. Installation alone does not prove catalog or provider access.

## Web and document operations

- Match the operation to the evidence job: Search discovers results; Scrape retrieves a supplied page; Map inventories site URLs without page bodies; Crawl collects a bounded multi-page section; Parse handles supported document files. Use a separately exposed extraction operation only according to its live schema.
- Reuse sufficient Search content. Read a known page when it can answer the question. Use structured JSON extraction for known fields and Markdown for readable content; keep crawl limits, paths, depth, subdomains, and external-link scope proportional to the task.
- Use Firecrawl Agent only for requested asynchronous multi-source research and resume it through the corresponding status tool. Do not start a duplicate while a job may still be active.
- Keep Developer Search and dedicated research-index tools on their native methods. General Search's `research` category is a website filter, not the paper index; do not assume an index call uses Alexandria execution.
- Interact can cause persistent website actions, and Monitor creates recurring external checks. Use them only for the corresponding authorized outcome.

Map returns URLs, not page bodies. Prefer a reading operation before Interact for a dynamic page. Prefer Firecrawl for site inventory, bounded collection, parsing, or structured extraction; TinyFish can serve a focused rendered-page read. Avoid duplicate successful reads across providers.

## Alexandria

Alexandria discovers structured data capabilities and executes them through Firecrawl. Use it when an unmet evidence need calls for comparable fields across entities, dated or precise records, or a collection that a suitable capability can supply. A sufficient search result or supplied document needs no extra discovery or paid enrichment. Before collecting the same fields from several pages, a targeted free discovery call can identify a more suitable route; do not browse the whole catalog routinely.

- **Discover before execution.** Search can return Alexandria matches alongside web results. For discovery alone, use `sources: ["alexandria"]` or a targeted `firecrawl_find_tools` query. Explicit web-only sources exclude semantic Alexandria matches; inspect the live defaults. Domain matching suggests tools but does not execute them, and a matching website alone does not establish suitability. Search `scrapeOptions` retrieves web pages, not provider data.
- **Inspect the selected contract.** Use `firecrawl_find_tools` with returned provider/capability IDs and `expand: ["options", "response"]` when Search returned compact summaries. Reuse a complete contract already returned; request examples only when needed. Check required inputs, `requiresOneOf`, geographic/time coverage, source fields, output shape, and the published price. Follow catalog `next` requests for further detail only as needed. Never invent provider IDs, capabilities, or inputs from a static example.
- **Choose on value and cost.** Discovery and domain matching are free; mixed web search and URL scraping retain their normal charges. Capability execution uses its listed credit price. Compare suitable routes without buying data from each to make the comparison. Honor existing budgets and authorization; clarify an unknown price or material unapproved spend before execution. Account for requested batches and additional pages; do not assume a provider call is cheaper than page extraction.
- **Execute only a discovered fit.** Prefer an existing supported MCP or CLI connection. In SDK integrations use `scrape({ alexandria: { provider, capability, options } })`; HTTP uses `POST /v2/scrape` with the same `alexandria` request body. Alexandria mode needs no URL. Adapt argument shapes to the live interface. Classify each capability and output mode under the shared synthesis, privacy, and action boundaries; the name `scrape` does not guarantee source-only retrieval.
- **Read the result contract.** Check each capability result for errors and actual source provenance. Use its declared response key rather than assuming `records`. Provider result pagination is separate from catalog navigation; preserve filters and bound additional pages. Retain and reuse `requestId` for retries of the identical execution payload, including uncertain or pending responses; do not generate a new ID to bypass a pending 409 or repeat a successful call because its output was not displayed.
- **Handle access boundaries.** If Alexandria is missing from the live schema, disclose the gap and use a permitted alternative. For `THIRD_PARTY_DATA_TERMS_REQUIRED`, show the returned `requiresAction.url` to an organization admin. Accepting terms requires explicit user authorization for the reviewed version and digest; discovery or research authorization is insufficient.
- **Report cost and evidence.** Name Firecrawl and the underlying provider/capability, identify useful returned fields and gaps, and report credits per call. Distinguish the published quote from response-reported usage; if actual usage is absent, label it unconfirmed rather than assuming a failed call was free. Do not attribute ordinary web evidence to Alexandria.

For current contracts and integration examples, see the [official Alexandria guide](https://docs.firecrawl.dev/features/alexandria). Do not maintain a fixed provider catalog or fixed execution prices here.

Report selected operations, material scope limits, freshness/access gaps, and asynchronous status proportionally. Follow applicable feedback instructions only within the user's authorization and avoid sending private research content.
